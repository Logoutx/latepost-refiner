# 说话人链路开发记录（dev trace）

说话人标签出问题时，最费时间的不是修，是找出它在哪一步坏的。这份记录把一次运行里说话人经过的每一步都写下来，让人不用读代码就能定位到具体阶段。

**默认关闭。它是开发排查工具，不是交付物，也不是运行日志。**

## 怎么打开

命令行加一个开关：

```bash
node universal/cli.js --files 访谈.md --topic 样本项目 --dev-trace
```

或者设环境变量（适合在脚本里临时打开）：

```bash
REFINER_DEV_TRACE=1 node universal/cli.js --files 访谈.md --topic 样本项目
```

用 `runJob()` 时传 `devTrace: true`。本地网页服务的接口参数会原样转给 `runJob()`，所以传 `devTrace: true` 也能开，但网页界面上没有这个开关——它不该出现在日常使用路径里。

关闭时这套代码是空操作：不建目录、不写文件、不做任何文件系统调用，`run.json` 与不带这个开关的运行逐字节一致。

## 记什么、不记什么

记的只有说话人的结构信息：

- 标签文字本身（例如“说话人 1 00”“记者”“林知远”）
- 行号、标签行数、说话人轨道数、各阶段的改写条数
- 侦察给出的建议标签、置信度、角色
- 兜底阶段发现的未知标签（行号 + 标签）
- 审计返回的数值指标（轮次数、错归数、参与人数等）

不记的：访谈正文、prompt、模型响应正文、网页正文、API key。这跟 `universal/trace.js` 是同一条隐私约定。

两个刻意的例外，都做了限长：

- 侦察阶段自己写的提醒里，只有提到“冲突”或“矛盾”的那几条会被记下来，每条截断到 80 个字符。
- 一行“看着像说话人标签却没被认成标签”的行，只记前缀加编号加后面那段纯数字符号（例如 `说话人 2 02：10`）；后面的部分只记字符数，写成 `…+4`，一个字都不带出来。

即便如此，记录里仍会出现真实人名（说话人标签就是人名）。它和成稿一样属于访谈材料，不要提交进仓库，也不要贴进 issue。

## 文件在哪

写在这次运行的输出目录下：

```
<输出目录>/.dev-trace/          目录权限 0700
  speaker-trace.jsonl          逐条事件，单轮内只追加，权限 0600；同一输出目录重跑时，
                               上一轮自动轮转为 speaker-trace-prev.jsonl / speaker-trace-prev.md，
                               当前文件永远只含本轮
  speaker-trace.md             人读的分阶段小结，运行结束时生成，权限 0600
```

这两个文件不会进 `run.json` 的产物清单（`artifacts`），飞书机器人不会看到它们。开了开关时，`run.json` 的 `execution.devTrace` 里会多出这两个路径，方便脚本找到它们；没开就没有这个字段。

## 怎么读 speaker-trace.md

说话人在一次运行里要过 6 关，小结按这个顺序逐份文件排开：

| 关 | 做什么 | 数字不对时说明 |
| --- | --- | --- |
| 1 解析源文件 | 认出哪些行是说话人标签，归成几条轨道 | 源文件本身或解析规则的问题——后面全都会跟着错 |
| 2 侦察认人 | 模型判断每条轨道是谁 | 模型没认出来，或分块之间给了矛盾答案 |
| 3 生成映射 | 把“源标签 → 输出标签”定下来 | 侦察结果没被采纳，或落到了 `unresolved` |
| 4 改写精校输入 | 把映射写进给精校用的副本 | 改写行数远小于标签行数，说明有轨道没被覆盖 |
| 5 成稿标签兜底 | 精校写回来后重新统一标签 | 出现“未知标签”就是模型自己造了一个人 |
| 6 审计核对 | 源稿与成稿逐轮比对归属 | 错归数大于 0，说明发言落到了别人名下 |

从上往下看，**第一处数字对不上的那一关就是问题发生的地方**。文件末尾的“疑似问题信号”把各关的异常汇总到一起，通常直接看这一节就够。

小结里有一个“近似漏判扫描”，它只看结构不看内容，回答 3 个问题：

- 有没有行看着像说话人标签，却没有被认成标签
- 有没有标签结尾挂着一段单独的数字（例如“张三 00”“说话人 1 00”）——这是时间戳被冒号切断的典型特征
- 靠冒号猜出来的弱标签，是不是比强标签还多——是的话，正文里的句子很容易被误当成标签

## 先跑 scripts/speaker-inspect.mjs

拿到一份可疑的源稿，第一件事不是开整条流水线，而是用这个只读小工具看一眼解析器眼里的结构。它不调模型、不写文件、几毫秒出结果：

```bash
node scripts/speaker-inspect.mjs 访谈.md
node scripts/speaker-inspect.mjs 访谈.md --json     # 给脚本用
```

打印说话人模式、标签行数、轨道数、逐轨道明细、纯源文件推断出的映射，以及上面那份近似漏判扫描——扫描逻辑与 dev trace 共用一份实现（`universal/speaker-trace.js` 导出的 `scanSpeakerNearMiss`），两边结论一定一致。

## 用 scripts/dev-trace-view.mjs 读记录

`speaker-trace.md` 要等运行结束才生成；运行中途、或者不想自己翻 JSONL 时，用阅读器：

```bash
node scripts/dev-trace-view.mjs <运行输出目录>              # 渲染 6 个阶段 + 疑似问题信号
node scripts/dev-trace-view.mjs <运行输出目录> --follow     # 跟着正在跑的任务实时打印，结束时给出完整视图
```

参数指到运行输出目录、`.dev-trace/` 目录或 `speaker-trace.jsonl` 都行。只读，不写任何文件；显示内容全部来自记录文件本身。

## 生产必须保持关闭

mac mini 上的 `lark-refine-bot` 只跑 Universal 运行时，且**不得**打开这个开关：它会在每个任务的输出目录里多写两个含人名的文件，属于额外的数据留存面，对生产没有任何用处。要排查线上的说话人问题，把那份源稿单独取下来，在本地开着开关重跑一次。
